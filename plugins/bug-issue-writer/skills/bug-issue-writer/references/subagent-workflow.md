# 通过 subagent 生成 issue

主代理负责分配、复核和汇总；子代理负责自己的报告。每份 issue 都执行 `SKILL.md` 中已有的核对和写作逻辑。

## 确定任务范围

1. 读取最新报告或缺陷清单，确认要处理的独立问题、源文件、测试、日志和输出位置。沿用已经确认的根因分组与编号，不把重复记录数当成 issue 数；无法判断是否重复时先保留区分并说明疑点。
2. 列出目标文件。用户要求 v2 时，在各问题目录生成 `*-submission-v2.md`，保留 v1 和用户确认的定稿；其他命名与覆盖方式服从用户要求及现有目录约定。
3. 将互不重叠的 issue 分给子代理。可以按模块分组，每个输出文件只有一个写入者；并行量根据可用槽位与任务规模决定，不固定模型或代理数量。
4. 主代理保留 `BUG-OVERVIEW.md` 及总目录索引的写入职责，避免多个代理同时覆盖汇总文件。

## 调用与任务交接

使用当前会话提供的子代理工具，例如 `spawn_agent` 或对已有代理的 `followup_task`。同一任务已有可用代理时可以继续使用；不依赖代理隐含继承了完整对话。

每次交接给出实际路径、明确文件清单和必要约束。下面的任务说明可按当前任务填写；不要只让代理“照上一份修改”。

```text
使用 {{SKILL.md 的绝对路径}} 及其 issue 模板，生成以下报告：
{{每项的问题标识、原报告或缺陷材料、目标输出文件}}

源码根目录：{{路径}}
测试与原始日志：{{各问题对应的路径}}
用户指定的最新定稿或额外要求：{{路径或具体要求；没有则省略}}

仅写入分配给你的目标报告文件。原测试、日志、源码、用户定稿及其他代理的文件保持不变。
按 skill 核对源码行号、完整测试和原始日志，保留影响结论的必要前提。
若源码表明原 bug 判断可能不成立，在 issue 标题后的首段标注“疑似不成立”并说明依据，完成汇报中一并指出，供主代理同步概览。
本任务只整理已有证据，不把历史记录写成新运行的结果。
不要更新总览或总目录，不再次委派，也不自行提交、推送或发布。
完成后汇报实际文件路径、完成情况，以及尚未解决的证据缺口。
```

若用户另外授权修改测试或执行验证，将具体范围传给对应代理，并按新的实际验证状态写报告，不机械套用上面的只读限制。

## 跟进与中断恢复

- 接收进度后核对文件；代理说“完成”不代表文件已经齐全或内容符合要求。主代理可同时审阅已完成的其他报告。
- 发现不符合写法或证据的问题，向原代理发出具体、局部的修订指令，指出文件和要改的段落。避免让它重写已经确认无误的部分。
- 代理中断时，先检查已落盘文件和未完成清单，再通过 `followup_task` 让原代理继续；原代理不可用时，将同一任务及进度交给替代代理。不要因中断覆盖用户改动或重复生成已完成文件。
- 恢复一次后仍遇到相同执行故障，由主代理接手剩余工作。缺少必要证据时保留真实缺口，按 skill 的草稿规则交付，不靠反复重试或编造结果凑齐完成状态。

## 主代理复核与汇总

1. 检查目标清单是否齐全、输出路径是否正确，确认没有改到受保护的报告、源码、测试或日志。
2. 阅读各份最终稿，并对照引用的源码行段、完整测试和对应原始日志；只有文字编辑时，测试应保持原样。检查单次日志摘录没有混入另一轮结果，也没有人工注释。
3. 确认必要限制仍在。例如有限轮询不能写成永久失效、未检查的能力清除不能写成已验证前提、边界用法不能扩大为正常用法的结论。
4. 完成局部修订后，再按 `overview-guide.md` 从这些最终稿生成或同步概览。复核子代理报告的“疑似不成立”及其源码依据，将尚未消除的疑点同步到概览开头和对应条目开头。待补证据和疑似不成立的条目均保留状态，不计入已确认缺陷。
5. 更新已有目录中指向这些报告的入口，并简短交付报告位置、概览位置和确实存在的缺口。写作任务无需另加完整调查记录。
