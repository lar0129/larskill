# Bug Issue Writer

把已有证据整理成维护者能直接理解、复现的 issue。读者不需要了解生成报告的 agent、内部测试框架或之前的对话。默认使用用户的语言，以已经确认的精简写法为准。

## 使用材料

- 新建报告时读取 [issue 模板](assets/issue-template.md)。如项目有必须填写的 issue 表单，将相同内容映射到其字段，不另加一份重复报告。
- 首次使用或需要把握详略时，读取 [用户确认的定稿样例](references/accepted-issue-example.md)。它展示写法；其中的项目版本、函数、运行环境、线程参数和错误地址仅属于该 bug。
- 修改已有报告时，先读用户最后保存的文件。用户的最新修改优先于旧稿和样例；不要补回用户已经删除的解释。

## 组织执行与交付

- 子代理工具可用且当前执行环境允许委派时，由主代理将 issue 写作分配给 subagent，使用 [子代理工作流程](references/subagent-workflow.md)。子代理沿用本 skill 的事实核对、模板和写作规则，不另起一套标准；已经作为写作子代理执行任务时，直接完成分配的文件，不继续委派。
- 主代理划定每个子任务的输入、输出文件和保护范围，复核实际产物后再汇总。用户要求直接完成或工具不支持子代理时，由主代理使用相同逻辑完成，不把未发生的委派写成已执行。
- 生成 issue 时，一并生成或更新报告总目录下的 `BUG-OVERVIEW.md`，遵循 [概览写法](references/overview-guide.md) 和 [概览模板](assets/overview-template.md)。主代理统一维护概览，提炼每份最终报告的预期行为、实际行为、影响和根因。
- 单篇定点修改不自动新建概览。已有概览需要同步且用户未限制修改范围时，只同步对应条目及相关开头标注、统计；不要因此重写其他报告或删除无关条目。

## 先核对事实

1. 从用户提供的材料中找到对应源码、测试程序和原始日志，核对函数、源码相对路径及行号。只读取支撑报告所需的上下文，不把写作任务扩展成完整的缺陷审计。
2. 对齐触发条件、函数应有行为、代码实际行为、测试输出和日志。按证据定位根因，不把原记录的目标函数直接当作出错函数。版本、架构、调度条件等仅在有依据且影响理解或复现时保留；不能借用样例中的值补齐未知信息。
3. 已有日志可以作为证据，不因整理文档而重跑整个测试流程，也不把历史记录写成本轮新执行的结果。编译通过不代表运行复现成功。若测试经过修改，旧日志不能冒充修改后代码的运行结果。
4. 先查已有材料，再询问真正缺失的关键信息。缺少运行记录时不能编造“实际输出”或报错日志；在对应位置简短说明尚未取得记录，交付时指出这是待补证据的草稿。不要用冗长的“验证边界”章节掩盖缺口。
5. 读完源码后，若发现原 bug 判断可能不成立，在 issue 标题后的首段标注 **疑似不成立**，简述疑点、源码依据及仍需核实的条件；同时在 `BUG-OVERVIEW.md` 标题后的开头提示和对应条目开头保留该状态。正文区分原报告主张与源码核对结果，不继续把存疑的错误、影响或根因写成定论，也不把疑点直接写成“已确认不是 bug”。仅缺少日志时标为待补证据；未重新运行测试不影响已有有效记录，两者均不自动标为疑似不成立。

## 报告写法

默认采用模板中的标题和三个正文小节。标题概括触发操作、错误行为及后果；不要把内部 bug 编号当作标题主体。

### 该问题是怎么引起的？

- 用一个短段落直接说明涉及的函数、触发条件和影响，再分别写 **期望行为**、**实际行为**。这里解释函数和代码，不在源码之前铺陈“本次测试构造了……”的测试过程。
- 写明“关键代码位于 `仓库相对路径` 第 X～Y 行”，随后贴足以看出问题的真实源码。可以节选，但保留决定错误路径的分支、更新和调用，不重构被报告的代码。
- 在错误发生处加少量代码注释，点明哪个状态改变了、哪个变量没有同步、后续哪次使用出错。注释解释缺陷，不逐行翻译正常代码。
- 源码后用一两段短文解释错误机制；存在明确先后关系时改用 Markdown `1. 2. 3.` 编号列表。步数由实际过程决定，不重复开头和代码注释的全部内容。

### 重现步骤

- 先用一个短段说明如何将测试接入项目、放到目标环境并执行。对于 QEMU，说明测试文件或程序名、适用产品或架构、放入镜像的位置和运行入口即可；只有影响触发的配置才需要说明。
- 不依赖 `fmprobe`、FM-Agent 或其他内部 agent 工具的命令。使用读者能识别的程序名和项目入口。默认不贴完整工具链安装、镜像构建、编译参数或测试流水线命令；项目必需的特殊步骤或用户明确要求的内容除外。
- 区分工具依赖和打印字符串：测试中的 `FM_OBSERVE` 等标签本身不构成内部工具依赖。不要为改名而改变已验证的测试；日志里重复表达同一结果的行可以省略。
- 用简短段落介绍测试逻辑；创建线程、等待、超时、唤醒等有顺序的操作使用编号列表。保留触发所需的输入、时序、优先级和调用顺序，不展开无关的调度或框架背景。
- 贴出完整测试代码，使读者能在说明的项目环境中使用。不要以省略号或“见附件”替代关键代码，也不要依赖未提供的私有辅助脚本。已验证的测试在仅做文字修改时保持不变；如为消除内部依赖而改写，应说明实际验证状态。
- 保留影响结果判断的测试限制，用一句话放在相关步骤旁。例如，专门验证错误路径的补读可能在修复后阻塞，不能将原测试不结束直接解释为缺陷仍存在。
- 测试代码后先写 **预期输出**，紧接着写 **实际输出**。预期输出描述正确实现应出现的结果；实际输出概括记录中真正出现的错误或停止位置，完整关键日志留到下一节。不为充实段落而反复罗列“未出现哪些后续输出”。

### 报错信息

- 从原始运行记录中摘出足以证明错误的关键行，放在 `text` 代码块中。保留必要的触发上下文、返回值、异常或断言信息；不要求每个 bug 都有崩溃或寄存器日志。
- 日志保持原文和先后顺序。可以省略无关的完整行，不改值、不美化字符串、不拼接不同运行造成假象。不要在日志里插入人工 `#`、`//`、箭头等解释；原始日志自带的 `#` 分隔线或注释照常保留。
- 在日志外用一两段短文指出哪几行或哪些字段体现错误，以及它们为什么与预期不符。只解释证明结论所需的部分；保留某行证据，不意味着必须对它逐项推导。
- 默认省略寄存器偏移验算、长调用链展开和重复的指针推导。若缺少某项解释就无法判断错误，可以保留最短的必要说明。

## 控制详略和修改范围

- 默认不增加录制编号及“摘自某次 QEMU 录制”、同文件其他函数对比、完整附件表、候选补丁、版本与验证边界、修复边界、本次编译核对等内容。必要的版本或环境用一句话放在相关位置；额外章节只按用户或项目表单的明确要求添加。
- 单篇 issue 正文自足，默认不加工作区绝对路径、证据目录链接、附件链接或额外外链。源码位置使用仓库相对路径和行号；用户或提交平台明确要求的链接除外。概览中的相对报告链接按概览模板保留。
- 普通说明用短段落，有顺序的过程用编号列表，并保留 Markdown 所需的空行。不要把每句话都拆成列表，也不照抄样例偶有的空格或排版瑕疵。
- 定点修改只改用户指出的部分，保留其余文字和测试。批量任务复用结构和写法，逐份核对各自事实；函数名、测试、预期结果和日志不能从另一份报告移植。
- 交付用户指定的报告及上述概览。写作本身不包含自动发布 issue、修改源码、生成理解指南或扩展到其他报告；提交和推送仓库变更也以用户授权为准。

## 交付前检查

- 读者能否从正文找到代码，理解函数的预期与实际行为，并用给出的测试触发问题？
- 源码解释是否紧贴关键代码，测试逻辑是否放在重现步骤中？有顺序的内容是否清楚呈现？
- 测试是否完整，预期输出和实际输出是否相邻，实际输出是否有对应记录？
- 日志是否保持原文、没有人工注释，正文是否指出足以判定错误的字段？
- 是否删掉内部工具上下文、额外链接及重复说明，且没有改动用户要求保留的内容？
- 主代理是否核对了每个子任务的实际文件？概览条目、计数和链接是否对应最终报告，且保留了影响结论的前提与证据限制？
- 源码核对发现的“疑似不成立”是否同时标在 issue 和概览开头、对应概览条目开头，附有简短依据，且未计入已确认缺陷？

校验文字与现有证据即可完成纯写作任务；只有代码变更、证据冲突或用户另有要求时，才进行相应的新验证。交付时简短说明文件位置和必要的缺口，不附上一轮调查过程。
