# 核查并记录一个 Bug

> 本文是 `plugins/bug-verifier/skills/verify-and-document-bug/SKILL.md` 的中文翻译，仅供阅读，不参与 skill 加载。

**frontmatter 字段**

- `name`: `verify-and-document-bug`
- `description`: 判断一个上报的 bug 是不是真缺陷，然后把它写清楚。只要有人指着一份 bug 文档 —— bug 报告、审计发现、静态分析命中、LLM 生成的发现、code review 评论、CTF 式的声称 —— 外加一份源码目录，希望核实、解释或转成 issue，就用这个 skill。它会读这份声称、读被指控的代码和触发用的测试，追查那个坏状态是否能从公开入口用调用者可控的参数到达，落一个结论（confirmed / latent / not a defect / undetermined），然后产出两份文档：一份 reviewer 不看别的东西就能决策的 issue 报告，一份把模块设计和缺陷所依赖的概念讲透的理解指南。

---

你会拿到一份 bug 文档和一份源码目录。你要交回一个判断和两份文档：一份 reviewer 单独看就能行动的 **issue 报告**，一份让读者真正理解这个缺陷的 **理解指南**。

判断在最前面。写一个不成立的 bug，消耗 reviewer 的注意力和真 bug 一样多，却什么都换不回来，所以绝不要跳过判断直接写文档。

## 输入

缺什么就问，不要猜：

- **bug 文档** —— 提出这个声称的报告、发现、审计记录或消息的路径。
- **源码目录** —— 这个声称所针对的代码树，如果分支或 commit 有影响，也一并要到。
- **输出目录** —— 两份文档放哪里。默认 `./bug-docs/`，并明确告知。

两份文档用 bug 文档的语言写，或者用户正在用的语言。跟着它，不要切换。

如果代码树有能跑的测试套件，现在就把命令找出来 —— 第 3 步要用。

## 第 1 步 —— 先按原文读这份声称

打开任何代码之前，先用它自己的说法把这些提取出来：

- 它指控的组件、文件、函数
- 它认为错的行为，以及它期望的行为
- 它说能触发这个问题的输入或调用序列
- 它拿出的证据：一个测试、一段日志、一个调用栈、一个 diff，还是什么都没有

读代码的过程中，声称会漂移。你需要把原始版本记下来，好用来对照。

## 第 2 步 —— 自己去读代码

绝不要相信声称里贴的片段。打开文件。

- 找到被指控的函数。记下真实路径和关键那几行的真实行号。
- 把整个函数读完，再看调用方传进来什么、拿返回值做什么。
- 向外追到**公开入口** —— syscall、ioctl、导出的 API、命令行参数、请求处理函数，这个模块的公开面是什么就追到什么。你需要一条真实的链条，每一跳都带 `file:line`；找不到就如实说找不到。这一步是真缺陷和构造缺陷的分界线。
- 读声称指向的那个测试，也读覆盖同一函数的相邻测试。一个通过的测试如果断言的正是被指控的行为，这就强烈提示"bug"其实是规格。
- 找出契约：文档注释、头文件文档、`Documentation/`、某个标准（POSIX、RFC、指令集手册）、代码断言的不变量，或者现有测试要求什么。缺陷是代码和契约之间的差距。如果你点不出契约，现在还不能叫它缺陷。
- 对这些行跑 `git log -L` 和 `git blame`。代码为什么长这样，答案通常就在写下它的那个 commit 里，而且理解指南会用到这段历史。

## 第 3 步 —— 试着触发它

跑那个被指名的测试，或者写一个最小的测试去走那条路径。记下确切的命令和确切的输出，包括失败输出。

如果什么都跑不了 —— 没有工具链、需要硬件、内核要跑在虚拟机里 —— 就在两份文档里都直说。"从源码推导，未实际执行"是一个正当的证据等级。声称自己跑了但其实没跑，不是。

## 第 4 步 —— 下判断

决定之前先读 `references/genuine-bug-criteria.md`。里面是一份报告必须过的四道闸门，以及用来抓构造 bug 的排除清单；那份清单就是这个 skill 的重点。

只落一个结论，并把它放在你写的任何东西的第一行：

- **Confirmed defect（确认缺陷）** —— 四道闸门全过，有复现或完整的入口路径支撑。
- **Latent defect（潜伏缺陷）** —— 代码确实是错的，但今天没有任何可达路径走到那里。真实，但优先级低。说清楚什么条件会让它变得可达。
- **Not a defect（不是缺陷）** —— 它需要公开面造不出来的状态，或者当前行为就是文档写明的行为，或者这只是风格偏好。
- **Undetermined（未定）** —— 点名那一件能把事情定下来的检查。

判定为 **not a defect** 时，跳过两份文档这套交付，只写一页：被声称的是什么、你用 `file:line` 核查了什么、卡在哪道闸门以及为什么、以及要让这个声称成立必须有什么前提为真。不要为了客气把它软化成"潜在问题"。也不要为了让这趟工作显得有价值而去另找一个 bug —— 如果路上顺手注意到了什么，用一两句提一下，和结论清楚地分开。

## 第 5 步 —— 写两份文档

用 `references/issue-report-template.md` 和 `references/understanding-guide-template.md`。按模版的章节顺序来。只有一个章节确实是空的才删掉它，而且要说明它是空的，不要拿废话填。

分工是：**报告用来决策和修复，指南用来学习。** 机制、行号、复现、修复方案进报告。模块用途、设计意图、陌生概念、正确行为的走查进指南。拿不定主意时，让报告保持短，让指南吸收背景。

## 证据规则

- 每段代码片段都从文件里复制出来，带真实路径和行号。绝不转述或重建代码。
- 每个关于运行时行为的断言都标等级：执行过、从源码追出来、还是推断的。
- 行号会漂移，所以把你读的那个 commit SHA 钉上。
- 如果你去找过某个东西但它不在那里，这本身就是一个发现。写下来。
- 把 bug 文档断言的内容和你核实过的内容清楚分开。

## 风格

`talk-like-a-human` skill 对两份文档都适用。简版：

- 结论先行。报告第一行就说什么坏了、有多严重。
- 用平实的词。术语第一次出现时就地解释，或者换一个读者本来就有的词。
- 一句话一个意思。
- 保留确切的数字、名字和条件。简洁是砍废话，不是砍事实。
- 散文和短列表优先于重型表格。只有真正是网格的数据才用表格。
- 不知道的事，坦率地说不知道。

## 交出去之前

以 reviewer 的身份而不是作者的身份，把两份文档重读一遍：

- 报告第一行说清楚什么坏了吗？
- 只看报告，他们能找到代码吗？
- 只看报告，他们能复现吗？
- 每段片段都是真的、每个行号都对着文件核过吗？
- 所有未核实的内容都标成未核实了吗？
- 报告里没解释就用掉的术语，指南里都解释了吗？
