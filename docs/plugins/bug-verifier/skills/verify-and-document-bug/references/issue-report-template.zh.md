# Issue 报告模版

> 本文是同目录下 `issue-report-template.md` 的中文翻译，仅供阅读。

一个读者，一件事：一位没看过那份 bug 文档、并且在决策之前不会去翻源码树的 reviewer。他们读完这一页，必须知道什么坏了、在哪里、怎么复现、以及修它要付什么代价。

存为 `<输出目录>/<slug>-issue.md`。slug 用 `组件-症状`，例如 `ext4-writeback-lost-flush`。

控制在一页半左右。背景放到理解指南里 —— 给个链接，不要内联进来。

## 结构

```markdown

**严重度：** <崩溃 / 数据丢失 / 结果错误 / 资源泄漏 / 挂死> —— <谁受影响>
**代码位置：** <仓库> @ <commit SHA>
**理解指南：** <相对路径>

## 概述

两三句话。什么坏了、在什么条件下、后果是什么。
只读到这里就停下的人，应该能把这个 bug 正确地复述回来。

​```c

​```

一两句话点名到底哪一行是错的、它做错了什么。

## 根因

三到六句讲机制：哪个值是错的、它是怎么变成那样的、它破坏了哪条不变量或契约、
以及这怎么变成了可见的失效。明确说出契约并引用它 —— 文档注释、标准、不变量或测试。

## 它是怎么被走到的

从公开入口到出错行的链条。每一跳都有引用。

1. `sys_entry()` —— `path/file.c:652` —— 调用者传入 `len = 0`
2. `middle_layer()` —— `path/file.c:578` —— 这里没有长度检查
3. `do_thing()` —— `path/file.c:130` —— 减法下溢

注明哪些输入由调用者控制，以及调用者能合法到达的任何前置条件
（没有打过补丁的代码、没有手搓的状态、没有仅供内部使用的入口）。

## 预期 vs 实际

**预期：** 按 `path/file.c:112` 的文档注释，`len == 0` 时 `do_thing()` 返回 `-EINVAL`。
**实际：** `len - 1` 回绕成 `SIZE_MAX`，`:131` 的循环越过缓冲区读取，进程收到 SIGSEGV。

## 影响

一次崩溃会不会拖垮调用者之外的东西？说最坏的现实情况，不是最坏的想象情况。

## 比结构更重要的规则

- **标题要承载 bug 本身。** `"ext4: 零长度写导致长度下溢并越界读取"` 好过 `"ext4 写路径有个 bug"`。reviewer 扫列表时是只看标题就做判断的。
- **片段是复制的，绝不是重打的。** 真实路径、真实行号、真实 commit。
- **预期和实际都要带来源。** 预期引契约。实际引那次运行或那条追出来的路径。
- **结论不要含糊。** 你在第 4 步已经决定了。写"可能有问题"会让 reviewer 把你的活重做一遍。
- **不要倾倒背景。** 设计历史、概念解释、模块导览都归指南。如果报告里确实需要一个 reviewer 可能没有的术语，用六个字就地解释，或者给链接。
- **把"别人告诉你的"和"你核实过的"分开。** 如果原 bug 文档声称了某件你无法确认的事，写"报告声称 X；我无法确认 X"，不要不声不响地照抄。
