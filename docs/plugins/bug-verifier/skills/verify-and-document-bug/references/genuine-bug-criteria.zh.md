# 什么样的缺陷才是真的

> 本文是同目录下 `genuine-bug-criteria.md` 的中文翻译，仅供阅读。

## 先把词分清，因为争论的胜负取决于它

测试实践把三件事分开，而混淆它们正是假 bug 被提上来的方式：

- **Error（错误）** —— 人犯的错：读错了规格、做了错的假设。
- **Defect（缺陷 / fault / "bug"）** —— 由此留在代码里的瑕疵。ISTQB 的定义：*工作产物中的一处不完善或缺失，使其不满足自身的需求或规格*。
- **Failure（失效）** —— 那个瑕疵被执行时可观察到的偏差：输出错误、崩溃、挂死、状态损坏。

所以缺陷是**代码和某个契约之间的差距**，失效是这个差距在运行时显现出来。一份既点不出契约、也点不出失效的报告，描述的不是缺陷 —— 它描述的是"有人不喜欢这段代码"。

同一条线在工业界的说法是：理论性的发现、以及没有实证运行时影响的静态分析输出，不算缺陷。反过来，判定"不是 bug"同样是一个实质性的断言，它也有举证责任：你必须确立那个坏状态在所讨论的上下文里不可达，而不只是说"要走到那里看着挺别扭"。

## 四道闸门

只有四条全部成立，报告才是真缺陷。按顺序检查，卡在第一个不通过的地方就停。

### 1. 能点名一个契约

指出代码违反了什么。以下之一：

- 描述预期行为的文档、文档注释或头文件
- 外部标准：POSIX、RFC、指令集或硬件手册、文件格式规范
- 代码自己断言或明显依赖的不变量（"页处于映射状态期间 `refcount > 0`"）
- 已经把预期行为编码进去的现有测试
- 没人写下来但所有人都假定的安全属性：不发生内存损坏、非特权用户不能让内核 panic、已持久化的写入不会丢、不能提权

如果唯一的论据是"我看着觉得不对"，那第 1 关就没过。如果当前行为**就是**文档写明的行为，这份报告最多是一个设计意见 —— 而在内核里，改变对用户可见的行为本身就是维护者拒绝的事，因为公开接口就是契约。

### 2. 从公开入口可达，且输入由调用者控制

写出从公开面到出错行的调用链，每一跳带 `file:line`：

```
sys_write() fs/read_write.c:652
  -> vfs_write() fs/read_write.c:578
    -> ext4_file_write_iter() fs/ext4/file.c:700
      -> 出错的分支 fs/ext4/file.c:742
```

"公开入口"指真实调用者从模块外部真正能调到的东西：syscall、ioctl、导出符号、网络处理函数、命令行参数、配置文件。并且，把执行导向坏分支的那些值，必须是调用者能自己选的 —— 直接选，或者通过一串普通调用间接选。

这一关是构造 bug 的死亡之地。可达性才是让一行可疑代码变成缺陷的东西；没有它，你手上只有一行代码，不是一个 bug。

### 3. 有可观察的坏结果

用代码之外的人也能看到的说法讲清楚出了什么问题：返回值或 errno 错误、数据损坏或丢失、panic 或 `BUG_ON`、死锁或活锁、内存或文件描述符泄漏、无界增长、某个权限检查被跳过、可测量的性能骤降。

"这段代码令人困惑"和"这里可以重构"都不是结果。"某个内部变量的值出人意料"也不是 —— 除非你把那个值一路带到某个可见的后果上。

### 4. 写得出触发条件

把前置条件和序列摊开：参数值、先前的状态以及调用者如何合法地到达那个状态、配置、并发。复现步骤必须最小且确定：没有多余步骤，每次跑结果一致。

如果是竞态，点名那个交错：哪两条路径、哪个共享对象、少了哪把锁或哪把锁被提前释放、以及哪种顺序导致失效。"高负载下偶尔崩"这一关没过。

## 排除项 —— 构造出来的 bug 会怎样自我暴露

以下任何一条成立，就判**不是缺陷**，最好的情况下也只是潜伏缺陷：

- **只能通过直接调内部辅助函数才到达。** 测试直接调了一个 `static` / 私有 / 未导出的函数，参数是任何公开调用者都不会产生的。
- **手搓出不可能的状态。** 准备阶段直接给结构体字段赋值、改内存、或把某个邻居 mock 成公开 API 永远造不出的状态。状态不可达，bug 就不可达。
- **违反了文档写明的前置条件。** 函数写着"调用者必须持有锁"或"`len` 必须非零"，而触发方式无视了它。那是测试自己写出来的调用方 bug，不是这个函数的 bug。
- **必须改代码才能触发。** 复现步骤里含一个补丁、一次注入的故障，或者一个没人用的编译选项。
- **可信调用方边界。** 输入在上游已经校验过，或者只有特权组件会提供它，而威胁模型里那个组件是可信的。说清是哪条边界、校验代码在哪。
- **测试把 bug 的前提当成了断言。** 新测试里那个"期望值"来自报告人的直觉，而现有测试套件和文档都认同当前行为。
- **不可达的防御性检查。** 断言的条件从外部确实造不出来。反面也要注意：如果它**确实**能被非特权调用者触发，那么一个会杀掉进程的断言就是真缺陷。内核里的 `BUG_ON` 正是因为用户态能通过 ioctl 踩到它才被删掉的。
- **不改变行为的小瑕疵。** 命名、格式、死代码、一个多余的检查。值得一个 cleanup patch，不值得一份 issue 报告。
- **症状挂错了位置。** 失效是真的，但被指控的那一行只是把它显现出来，缺陷在别处。报到修复该落地的地方去。

## 灰色区域，如实命名

- **潜伏缺陷（latent defect）** —— 代码是错的，一旦被走到就会失效，但当前没有路径走到它。就说"潜伏"，并说清什么会暴露它（一个新调用方、某个配置、未来一次重构）。不要抬成 confirmed，也不要当假的驳回。
- **缺功能 vs 缺陷** —— 需求承诺过但代码里没有的行为是缺陷；没人承诺过的行为是功能请求。
- **规格本身错了** —— 代码符合文档，文档与标准矛盾。这是真问题，但修复是一个决策而不是一个补丁。当成规格问题提出来，两边都引上。
- **可达但无害** —— 路径存在，值也确实古怪，但下游什么都不受影响。第 3 关不过。直说。

## 证据阶梯

给自己的证据定级，并把级别写进报告：

1. **Executed（执行过）** —— 你跑了测试或程序，抓到了失败输出。最强。
2. **Traced（追出来的）** —— 从源码读出从入口到故障点的完整路径，每一跳都有引用，但什么都没跑。
3. **Inferred（推断的）** —— 推理说得通，但有一处你没能闭合的缺口。说清缺口在哪。

绝不要把第 3 级当第 1 级呈现。一份写着"从源码追出来，未执行"的报告仍然有用；一份夸大其词、在 reviewer 第一次核对时就崩掉的报告，会让你之后每一份报告都失去信任。
